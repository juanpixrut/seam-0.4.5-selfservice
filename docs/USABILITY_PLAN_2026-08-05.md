# Seam AMS — path to a usable asset management system

Date: 2026-08-05
Scope: what's missing to complete a real, full asset-management cycle — functional gaps, not code quality or technical debt.

---

## The headline finding

You said "asymptotically close" and asked what's missing to compound into something usable. Having gone through the actual code, not memory of it, here's the honest answer: **the registry half of this system is genuinely solid. The monitoring half doesn't exist as a live system yet — it's three real, well-built pieces of infrastructure that have never been connected to each other.**

Specifically: `internal/rules/engine.go` is a complete, real rule-evaluation engine. It is never called from anywhere in the live application. `internal/webhook`'s delivery service is fully built and wired into the handler. Nothing ever calls it. There is no endpoint anywhere for a sensor to push a reading in. Every alert and event you can see in the running app right now is seed data — nothing in the system currently *creates* one.

That's not a UI gap or a missing button. It's the difference between "a system that manages a static registry of things you own" and "a system that manages those things." The second is what "asset management" usually promises, and it's the part that's actually missing — not 90% missing, *entirely* missing, end to end.

## What's genuinely solid (don't touch, don't worry about)

| Area | State |
|---|---|
| Asset registry | Real. 42-field dynamic form, full asset-type/property system, masters data (brands, models, regions, locations, custodians, currencies, cost centers) all with real CRUD, asset hierarchy via a real search-and-pick widget. |
| People & access | Real. User CRUD, role-based permissions, three genuinely separated modules (Account/Settings/Administration) with independent gating. |
| Alerts (the human half) | Real. List, detail, acknowledge, resolve all work — *if* an alert exists to act on. |
| Sensor-asset binding | Real, just built. Search, bind, unbind, all live-verified. |
| i18n | Real and thorough across four locales, including the redirect-encoding fix. |

This is a lot of genuinely working surface area. The gap isn't breadth of features — it's that the one loop that turns "a registry" into "a management system" was never closed.

## The critical path, walked end to end

This is the sequence a real user would actually try to run, and exactly where it breaks:

1. Register an asset — **works**
2. Bind a sensor to it — **works** (just built)
3. The sensor reports something abnormal — **no path exists.** There is no endpoint for a sensor (real or simulated) to submit a reading. Events in the running system only exist because a seed script inserted them directly.
4. A rule evaluates the reading and decides whether to raise an alert — **the engine exists and is never called.** Nothing invokes it when an event arrives, because nothing invokes it, period.
5. An alert appears for someone to see — **only if step 4 happened, which it doesn't.**
6. Someone acknowledges/resolves the alert — **works**, once an alert exists.
7. Someone creates a work order to actually fix the problem — **Work Orders exists but is gated off by default**, has no link from an alert at all (you can't go from "this alert" to "a work order for this"), and its FSM is a 3-state minimum (draft → in_progress → completed) built as a composition proof, not a scoped feature.
8. The asset's own history reflects that something happened and was fixed — **doesn't propagate anywhere.** A completed work order is its own record; nothing about it touches the asset it was for.
9. Eventually the asset is retired — **possible, but only by hand-editing the status field.** No dedicated action, no reason captured, no audit trail of the transition.

Steps 1, 2, 6 work. Steps 3, 4, 5, 7, 8, 9 don't — and 3→4→5 is one connected failure, not three separate ones.

## What I'd actually build first — small, compounding, in this order

The instinct that "a few things compound" is right. Here's what I think those things are, ordered so each one makes the next one meaningful rather than sitting alone:

### 1. Event ingestion — the missing front door
One real endpoint: a sensor (or a script standing in for one) can submit a reading against a bound asset. Doesn't need to be sophisticated — it needs to *exist*. Without this, nothing downstream has anything to react to, no matter how good the rule engine is.

### 2. Wire the rule engine to actually fire
Connect event ingestion → `internal/rules/engine.go` → alert creation. This is the single highest-leverage piece on this whole list: the engine is *already built*. This isn't "build a rules engine," it's "call the one that exists." Once this is live, alerts stop being seed data and start being real signals a real user generated by doing something.

### 3. Alert → Work Order, one link
From an alert's own detail page, one action: "create a work order for this." Doesn't need automatic triggering yet — a manual link is enough to close the loop the first time. This is what turns "the system told me something's wrong" into "the system helped me do something about it."

### 4. Turn Work Orders from playground into a real, scoped feature
Not the full CMMS vision (T-11's Blocks/Numbering/Business Rules/Cuadrilla/Empresa can stay deferred). Just: flip `EnableWorkOrders` on by default, give it real permissions instead of "any authenticated user," and make its completion write something back to the asset it was for — even just a status note or a lifecycle event. That's steps 7 and 8 closed together.

### 5. A dedicated "retire this asset" action
Small, but real: a purpose-built action instead of hand-editing a status field, capturing a reason and a timestamp. Closes step 9 without needing to be elaborate.

Five items. The first three are the actual compounding core — they turn on the entire monitoring half of the system, which currently doesn't exist at all. The fourth and fifth close what's left of the lifecycle around it.

## What I'd explicitly *not* build yet

Worth being just as clear about this, since "usable" is a scope decision, not just an addition:

- **The full Documents module.** Its own spec depends on three external services (seam-filer, fijuggler, thumble) that may not even be running. A real management cycle doesn't strictly need document attachment to be usable — it needs the monitoring loop closed first. Revisit once the rest of this list is real.
- **Data export/reporting.** Genuinely absent (the only "export" in the whole app is an FSM diagram as a PNG), and genuinely worth having eventually, but it's a reporting layer on top of a working system — not part of what makes the system work in the first place.
- **The full CMMS vision** (T-11) — Blocks, Numbering, Business Rules, Cuadrilla/Empresa as real entities. The scoped-down Work Orders from item 4 above is enough to close the loop; the fuller vision is real, separate, later work.
- **Automatic rule-triggered work order creation.** Manual linking (item 3) is enough to prove and use the connection. Automatic creation is a natural next step once the manual path is trusted.

## What I need from you before starting

Two real decisions, not things I should guess at:

1. **How should a sensor actually submit a reading?** A simple authenticated POST endpoint is the obvious shape, but if there's a real device/protocol expectation (MQTT, a specific payload format, a gateway device) I should build against that instead of inventing something that gets thrown away later.
2. **What should a rule's condition/action shape actually look like for a first real use?** The engine exists but I haven't yet checked how expressive it already is versus what a first real rule would need — worth me digging into that once we're aligned on this being the plan, rather than guessing here.

Everything else on this list I'm confident enough to just start on.
